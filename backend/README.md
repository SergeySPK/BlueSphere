# Blue Sphere — Backend

Backend приложения **Blue Sphere** — серверная часть школьного приложения. Реализован на Python с использованием FastAPI, SQLAlchemy и PostgreSQL.

Backend предоставляет REST API для работы со школами, учебными годами, классами, расписанием, учебной нагрузкой, рекомендациями и статистикой опросов. Также он отвечает за авторизацию пользователей через MAX Mini App, управление доступом, прохождение опросов через MAX, отправку уведомлений и фоновый AI-анализ учебной нагрузки.

## 1. Технологический стек

- **Python 3.13** — язык разработки.
- **FastAPI** — REST API.
- **Uvicorn** — ASGI-сервер.
- **SQLAlchemy 2** — ORM и работа с базой данных.
- **PostgreSQL** — основная СУБД.
- **Alembic** — миграции схемы базы данных.
- **Pydantic** — валидация и сериализация данных.
- **psycopg** — драйвер PostgreSQL.
- **PyJWT** — создание и проверка JWT.
- **maxapi** — взаимодействие с MAX.
- **python-dotenv** — загрузка переменных окружения.
- **Pytest** — автоматизированное тестирование.
- **uv** — управление зависимостями и виртуальным окружением.

## 3. Основные функциональные возможности

### 3.1. Школы и учебный процесс

Система поддерживает работу с несколькими школами и учебными годами.

Основные сущности:

- школы и их часовые пояса;
- учебные годы;
- классы;
- ученики и зачисления в классы;
- учителя;
- предметы;
- предметные назначения учителей;
- права доступа учителей к классам;
- расписание;
- сессии редактирования расписания.

Данные школ и учебных лет изолированы с помощью связей и ограничений целостности PostgreSQL.

### 3.2. Расписание и учебная нагрузка

API предоставляет:

- получение расписания класса;
- получение сводной информации о нагрузке;
- отображение дневной нагрузки;
- получение рекомендаций по изменению распределения нагрузки;
- редактирование занятий;
- управление сессиями редактирования.

Сессии редактирования позволяют контролировать одновременное изменение расписания и права пользователя на выполнение операции.

### 3.3. Авторизация

Основной механизм авторизации связан с MAX Mini App.

Пользователь передаёт `initData`, сервер проверяет данные авторизации и выдаёт JWT-токен. Защищённые маршруты используют токен для определения пользователя и проверки разрешений.

В проекте также предусмотрен отдельный маршрут демонстрационной авторизации. Он доступен при `DEMO_MODE=true`.

### 3.4. Роли и разграничение доступа

В системе предусмотрены три основные роли:

- **Ученик** — доступ к собственной школе, классу и доступным ему функциям.
- **Учитель** — доступ к разрешённым классам и функциям управления учебным процессом.
- **Администратор** — доступ к данным своей школы и административным операциям.

Пользователь может иметь несколько ролей. Разрешения проверяются на стороне backend.

Доступ учителя к классу хранится в отдельной таблице `TeacherClassAccess`. Предметные назначения `TeachingAssignment` и права доступа к классу являются разными сущностями.

При переносе предметных назначений между учителями система сохраняет целостность расписания и отдельно управляет правами доступа. Перенос выполняется с проверкой школы, учебного года, выбранных классов и конфликтующих назначений.

### 3.5. Опросы

Система опросов включает:

- шаблоны и экземпляры опросов;
- вопросы и варианты ответов;
- уведомления ученикам;
- сохранение одиночных и множественных ответов;
- управление черновиками;
- отслеживание прогресса прохождения;
- закрытие просроченных опросов;
- получение агрегированной статистики.

Прогресс прохождения хранится в `SurveyNotification`.

Поддерживаются состояния:

| Статус | Значение |
|---|---|
| `not_started` | Ученик ещё не начал опрос |
| `in_progress` | Опрос начат |
| `completed` | Опрос завершён |
| `closed` | Время прохождения завершилось |

Для отслеживания прохождения сохраняются время начала, завершения и закрытия, а также идентификатор сообщения MAX.

Повторная обработка callback и повторные вызовы отправки учитывают текущее состояние прохождения, чтобы не создавать дубликаты вопросов и не нарушать сохранённый прогресс.

### 3.6. Статистика опросов и конфиденциальность

API предоставляет агрегированную статистику по опросам с учётом прав доступа.

- Ученик получает статистику только своего класса.
- Учитель получает статистику классов, к которым у него есть доступ в соответствующем учебном году.
- Администратор получает статистику классов своей школы.

Состав участников определяется по зачислениям учеников на дату проведения опроса.

Статистика отображается в агрегированном виде. Минимальный порог количества ответивших не установлен: агрегированные результаты доступны и для небольших групп.

Индивидуальные ответы и идентификаторы учеников через статистические API не раскрываются.

### 3.7. MAX-бот и отправка уведомлений

Взаимодействие с MAX разделено на два модуля:

- `max_bot.py` обрабатывает входящие события, команду `/start` и callback-кнопки;
- `max_sender.py` отправляет приглашения и вопросы опросов.

Отправка и прохождение опроса учитывают сохранённый прогресс ученика. Повторная отправка не должна повторно запускать уже начатое прохождение.

### 3.8. Планировщик

`scheduler.py` отвечает за обработку очереди уведомлений, контроль сроков опросов и постановку задач AI-анализа.

Реализованы:

- проверка временных окон отправки с учётом часового пояса школы;
- пакетная обработка уведомлений;
- ограничение количества попыток;
- повторные попытки отправки;
- восстановление зависших отправок;
- heartbeat и lease для контроля выполняющейся задачи;
- защита от устаревших попыток отправки;
- закрытие просроченных прохождений;
- удаление неактуальных черновиков;
- ежедневная постановка AI-задач для школ.

Основные параметры планировщика:

| Параметр | Значение |
|---|---:|
| Интервал проверки очереди | 60 секунд |
| Максимум попыток отправки | 3 |
| Тайм-аут зависшей отправки | 10 минут |
| Размер пакета уведомлений | 20 |
| Интервал heartbeat | 60 секунд |
| Задержка повторной попытки | 5 минут |

Временные окна опросов задаются по местному времени школы:

- день проведения опроса: 18:00–22:00;
- следующий день: 08:00–18:00;
- после окончания окна отправка прекращается.

**Безопасный режим:** реальная отправка уведомлений отключена по умолчанию. Для её включения используется `SEND_NOTIFICATIONS=true`.

Не включайте отправку на рабочей базе без проверки конфигурации и отдельного подтверждения.

### 3.9. AI-анализ и рекомендации

AI-подсистема предназначена для анализа учебной нагрузки класса и формирования рекомендаций по её распределению.

Она состоит из очереди заданий, планировщика, фонового worker, модуля подготовки контекста, AI-провайдера и слоя сохранения результатов.

#### Постановка задач

Планировщик проверяет местное время каждой школы. В 22:00 по часовому поясу школы он ставит задачу ежедневного AI-анализа.

Повторная постановка защищена ключом дедупликации. Для одной школы и локальной даты не должны создаваться дублирующие задачи.

Если AI-провайдер не настроен, новые AI-задачи не ставятся.

#### Обработка задач

`ai_worker.py` — отдельный постоянно работающий процесс.

Worker:

- получает задачи из очереди;
- захватывает задачу с ограниченной по времени арендой;
- собирает данные расписания и агрегированные результаты опросов;
- выполняет AI-анализ;
- проверяет структуру ответа;
- сохраняет прогнозы и рекомендации;
- повторяет обработку задач при временных ошибках.

Worker опрашивает очередь с интервалом 5 секунд. Для контроля выполнения используются lease и heartbeat.

#### Входные данные AI

AI использует:

- расписание конкретного класса;
- типы занятий и предметы;
- даты занятий;
- агрегированные результаты закрытых опросов.

Персональные ответы учеников и идентификаторы учеников не передаются в AI-контекст.

AI-анализ выполняется в разрезе классов. Результаты разных классов не объединяются в общую рекомендацию для учителя.

#### Прогноз нагрузки

Для каждой даты сохраняется уровень нагрузки:

| Уровень | Значение |
|---:|---|
| `0` | Перегрузка |
| `1` | Высокая нагрузка |
| `2` | Средняя нагрузка |
| `3` | Низкая нагрузка |
| `4` | Лёгкая нагрузка |
| `None` | В этот день нет уроков |

Если на дату нет занятий, уровень автоматически устанавливается в `None`, а AI-анализ этой даты не выполняется.

Уровни сохраняются в таблице `ai_daily_forecasts`. Это канонический источник данных для тепловой карты и сводки.

Наступившие и прошедшие даты не должны изменяться последующими AI-анализами. Ответы на опросы за текущий день могут влиять только на будущие прогнозы.

#### Рекомендации

AI может формировать рекомендации трёх видов:

- `class` — рекомендация для класса;
- `teacher` — рекомендация для учителя;
- `lesson` — рекомендация по конкретному занятию.

Приоритет рекомендации:

- `low`;
- `normal`;
- `high`;
- `critical`.

Рекомендации сохраняются отдельно от дневных прогнозов. Доступ к ним ограничен ролью пользователя и его правами на класс и назначения.

Ученики не имеют доступа к AI-рекомендациям.

#### Провайдеры и резервная конфигурация

AI-провайдер задаётся через переменные окружения `AI_BASE_URL`, `AI_TOKEN` и `AI_MODEL`.

Предусмотрен резервный провайдер через `AI_FALLBACK_BASE_URL`, `AI_FALLBACK_TOKEN` и `AI_FALLBACK_MODEL`.

Это позволяет менять используемую AI-модель и endpoint без изменения бизнес-логики приложения.

Если основной провайдер не настроен, AI-обработка отключается, но REST API и остальные процессы могут работать без AI-конфигурации.

## 4. Подготовка окружения

Для локальной разработки необходимы:

- Python 3.13;
- uv;
- PostgreSQL.

Перейдите в каталог backend:

```bash
cd backend
```

Создайте файл окружения из примера:

```bash
cp .env.example .env
```

Заполните необходимые значения в `.env`.

Создайте виртуальное окружение и установите зависимости:

```bash
uv sync --dev
```

Команда устанавливает зависимости проекта из `pyproject.toml` с учётом версий, зафиксированных в `uv.lock`.

### DEMO_MODE

`DEMO_MODE` — переключатель режима работы с пользователями.

- `DEMO_MODE=false` — обычный режим. Реальные пользователи авторизуются через MAX Mini App с валидными `initData`.
- `DEMO_MODE=true` — демонстрационный режим. Разрешается создание тестовых пользователей через демонстрационную авторизацию API, например через Swagger или `curl`.

Для стандартного сценария проверки приложения через MAX необходимо использовать `DEMO_MODE=false`.

`DEMO_MODE` не является переключателем всей инфраструктуры и не включает автоматически тестовые данные. Наполнение базы демонстрационными данными выполняется отдельными seed-скриптами.

### SEND_NOTIFICATIONS

- `SEND_NOTIFICATIONS=false` — планировщик не отправляет реальные уведомления.
- `SEND_NOTIFICATIONS=true` — разрешена реальная отправка сообщений через MAX.

Для первоначальной настройки и проверки рекомендуется использовать `false`.

**Важно:** в Docker Compose по умолчанию задано значение `true`, если переменная не передана. Поэтому в `.env` необходимо явно указывать:

```env
SEND_NOTIFICATIONS=false
```

### AI-конфигурация

Для включения основного AI-провайдера должны быть заполнены все три переменные:

```env
AI_BASE_URL=
AI_TOKEN=
AI_MODEL=
```

Резервный провайдер необязателен. Если он используется, необходимо заполнить все три переменные:

```env
AI_FALLBACK_BASE_URL=
AI_FALLBACK_TOKEN=
AI_FALLBACK_MODEL=
```

Дополнительные параметры:

```env
AI_TIMEOUT_SECONDS=60
AI_MAX_OUTPUT_TOKENS=4000
```

Если основной AI-провайдер не настроен, планировщик не ставит ежедневные AI-задачи, а worker не забирает задания из очереди.

### Безопасность

- Не добавляйте `.env` в Git.
- Не публикуйте токены и секретные ключи.
- Не используйте рабочую базу для тестов.
- Не включайте `SEND_NOTIFICATIONS=true` без проверки целевого окружения.
- Не передавайте production-секреты в документацию и исходный код.

## 6. Работа с базой данных и миграциями

Для управления схемой PostgreSQL используется Alembic.

Все команды ниже выполняются из каталога `backend`.

Перед применением миграций проверьте подключение и целевую базу данных.

Посмотреть текущую ревизию:

```bash
uv run alembic current
```

Посмотреть историю миграций:

```bash
uv run alembic history
```

Посмотреть SQL, который будет выполнен при обновлении:

```bash
uv run alembic upgrade head --sql
```

Применить миграции:

```bash
uv run alembic upgrade head
```

**Важно:** миграции изменяют структуру базы данных. Перед применением на рабочей базе необходимо проверить целевое подключение, изучить миграции и подготовить резервную копию. Не запускайте миграции на production без отдельной проверки.

Новые изменения структуры БД оформляются отдельными миграциями Alembic. Не изменяйте уже применённые миграции вместо создания новых.

При локальном запуске через Docker Compose миграции автоматически выполняются командой запуска API-контейнера.

При отдельном развёртывании через Bothost миграции необходимо контролировать отдельно: запуск API через универсальный Dockerfile сам по себе не заменяет проверку и применение миграций.

## 7. Запуск компонентов

Команды ниже выполняются из каталога `backend`.

### 7.1. REST API

```bash

```

После запуска:

- Swagger UI: `http://127.0.0.1:8000/docs`
- OpenAPI JSON: `http://127.0.0.1:8000/openapi.json`

Для остановки нажмите `Ctrl+C`.

Параметр `--reload` предназначен для локальной разработки.

### 7.2. MAX-бот

```bash
uv run python max_bot.py
```

Для работы необходимы `BOT_TOKEN` и доступ к той же базе данных, с которой работает API.

### 7.3. Планировщик

```bash
uv run python scheduler.py
```

Планировщик работает постоянно и выполняет цикл проверки каждую минуту.

По умолчанию реальные уведомления отключены.

Для включения отправки необходимо явно установить:

```env
SEND_NOTIFICATIONS=true
```

Перед включением убедитесь, что используется нужная база данных и правильный токен MAX.

### 7.4. AI Worker

```bash
uv run python ai_worker.py
```

AI Worker — отдельный постоянно работающий процесс, который обрабатывает очередь AI-задач.

Для его работы необходимы:

- доступ к той же базе данных, что и у API и планировщика;
- настроенный основной AI-провайдер;
- при необходимости — резервный AI-провайдер.

Worker можно запустить без AI-конфигурации, но в таком случае он не будет забирать задачи из очереди.

Для штатной работы worker должен быть запущен постоянно и автоматически перезапускаться при аварийном завершении.

## 11. Docker и развёртывание

### 11.1. Docker Compose

В корне репозитория находится `docker-compose.yml`.

Он описывает следующие сервисы:

| Сервис | Назначение |
|---|---|
| `postgres` | PostgreSQL 16 |
| `api` | REST API |
| `bot` | MAX-бот |
| `scheduler` | Планировщик уведомлений и AI-задач |
| `ai-worker` | Фоновая обработка AI-задач |

Данные PostgreSQL сохраняются в Docker volume `postgres_data`.

Для запуска из корня репозитория:

```bash
docker compose --env-file backend/.env up -d --build
```

Посмотреть состояние контейнеров:

```bash
docker compose --env-file backend/.env ps
```

Посмотреть логи всех сервисов:

```bash
docker compose --env-file backend/.env logs -f
```

Посмотреть логи отдельного сервиса:

```bash
docker compose --env-file backend/.env logs -f api
docker compose --env-file backend/.env logs -f scheduler
docker compose --env-file backend/.env logs -f ai-worker
```

Остановить контейнеры:

```bash
docker compose --env-file backend/.env down
```

Команда `down` не удаляет volume с данными PostgreSQL.

**Не используйте `docker compose down -v`, если не планируете удалить данные базы.**

API-контейнер при запуске выполняет:

```bash
alembic upgrade head
```

После этого запускается Uvicorn.

Остальные процессы используют ту же базу данных. При первом запуске убедитесь, что API завершил миграции до начала работы остальных компонентов.

### 11.2. Dockerfile отдельных компонентов

В каталоге `backend` предусмотрены отдельные Dockerfile:

- `Dockerfile.api` — REST API;
- `Dockerfile.bot` — MAX-бот;
- `Dockerfile.scheduler` — планировщик;
- `Dockerfile.ai-worker` — AI Worker.

## 12. Правила разработки

1. Изменения структуры БД оформляются новыми миграциями Alembic.
2. ORM-модели размещаются в `models.py`.
3. API-маршруты и проверки доступа находятся в `main.py`.
4. Логику работы с опросами следует размещать в соответствующих сервисных модулях.
5. Обработку событий MAX и отправку сообщений необходимо сохранять разделёнными между `max_bot.py` и `max_sender.py`.
6. Логику очереди и повторных попыток уведомлений следует поддерживать в `scheduler.py`.
7. AI-логику следует разделять между конфигурацией, подготовкой контекста, провайдером, схемами, сервисом, очередью и worker.
8. Новая функциональность должна сопровождаться автоматизированными тестами.
9. Тесты должны использовать отдельную тестовую базу данных.
10. Необходимо сохранять транзакционную целостность, проверки прав доступа и защиту от повторной обработки операций.
11. AI не должен получать персональные ответы учеников и идентификаторы учеников.
12. AI может изменять только разрешённые прогнозные данные и рекомендации; источником отображаемой нагрузки остаются сохранённые прогнозы.
13. Реальную отправку сообщений MAX нельзя включать без проверки окружения и явного разрешения.
