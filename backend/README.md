# Blue Sphere — Backend

Backend приложения **Blue Sphere** — серверная часть школьного приложения. Реализован на Python с использованием FastAPI, SQLAlchemy и PostgreSQL.

Backend предоставляет REST API для работы со школами, учебными годами, классами, расписанием, учебной нагрузкой, рекомендациями и статистикой опросов. Также он отвечает за авторизацию пользователей через MAX Mini App, управление доступом, прохождение опросов через MAX и отправку уведомлений.

## 1. Технологический стек

- **Python 3.13** — язык разработки.
- **FastAPI** — REST API.
- **Uvicorn** — ASGI-сервер.
- **SQLAlchemy 2** — ORM и работа с базой данных.
- **PostgreSQL** — основная СУБД.
- **Alembic** — миграции схемы базы данных.
- **Pydantic** — валидация и сериализация данных.
- **psycopg** — драйвер PostgreSQL.
- **PyJWT** — создание и проверка JWT.
- **maxapi** — взаимодействие с MAX.
- **python-dotenv** — загрузка переменных окружения.
- **Pytest** — автоматизированное тестирование.
- **uv** — управление зависимостями и виртуальным окружением.

## 3. Основные функциональные возможности

### 3.1. Школы и учебный процесс

Система поддерживает работу с несколькими школами и учебными годами.

Основные сущности:

- школы и их часовые пояса;
- учебные годы;
- классы;
- ученики и зачисления в классы;
- учителя;
- предметы;
- предметные назначения учителей;
- права доступа учителей к классам;
- расписание;
- сессии редактирования расписания.

Данные школ и учебных лет изолированы с помощью связей и ограничений целостности PostgreSQL.

### 3.2. Расписание и учебная нагрузка

API предоставляет:

- получение расписания класса;
- получение сводной информации о нагрузке;
- отображение дневной нагрузки;
- получение рекомендаций по изменению распределения нагрузки;
- редактирование занятий;
- управление сессиями редактирования.

Сессии редактирования позволяют контролировать одновременное изменение расписания и права пользователя на выполнение операции.

### 3.3. Авторизация

Основной механизм авторизации связан с MAX Mini App.

Пользователь передаёт `initData`, сервер проверяет данные авторизации и выдаёт JWT-токен. Защищённые маршруты используют токен для определения пользователя и проверки разрешений.

В проекте также предусмотрен отдельный маршрут демонстрационной авторизации.

### 3.4. Роли и разграничение доступа

В системе предусмотрены три основные роли:

- **Ученик** — доступ к собственной школе, классу и доступным ему функциям.
- **Учитель** — доступ к разрешённым классам и функциям управления учебным процессом.
- **Администратор** — доступ к данным своей школы и административным операциям.

Пользователь может иметь несколько ролей. Разрешения проверяются на стороне backend.

Доступ учителя к классу хранится в отдельной таблице `TeacherClassAccess`. Предметные назначения `TeachingAssignment` и права доступа к классу являются разными сущностями.

При переносе предметных назначений между учителями система сохраняет целостность расписания и отдельно управляет правами доступа. Перенос выполняется с проверкой школы, учебного года, выбранных классов и конфликтующих назначений.

### 3.5. Опросы

Система опросов включает:

- шаблоны и экземпляры опросов;
- вопросы и варианты ответов;
- уведомления ученикам;
- сохранение одиночных и множественных ответов;
- управление черновиками;
- отслеживание прогресса прохождения;
- закрытие просроченных опросов;
- получение агрегированной статистики.

Прогресс прохождения хранится в `SurveyNotification`.

Поддерживаются состояния:

| Статус | Значение |
|---|---|
| `not_started` | Ученик ещё не начал опрос |
| `in_progress` | Опрос начат |
| `completed` | Опрос завершён |
| `closed` | Время прохождения завершилось |

Для отслеживания прохождения сохраняются время начала, завершения и закрытия, а также идентификатор сообщения MAX.

Повторная обработка callback и повторные вызовы отправки учитывают текущее состояние прохождения, чтобы не создавать дубликаты вопросов и не нарушать сохранённый прогресс.

### 3.6. Статистика опросов и конфиденциальность

API предоставляет агрегированную статистику по опросам с учётом прав доступа.

- Ученик получает статистику только своего класса.
- Учитель получает статистику классов, к которым у него есть доступ в соответствующем учебном году.
- Администратор получает статистику классов своей школы.

Состав участников определяется по зачислениям учеников на дату проведения опроса.

Статистика отображается в агрегированном виде. Минимальный порог количества ответивших не установлен: агрегированные результаты доступны и для небольших групп.

Индивидуальные ответы и идентификаторы учеников через статистические API не раскрываются.

### 3.7. MAX-бот и отправка уведомлений

Взаимодействие с MAX разделено на два модуля:

- `max_bot.py` обрабатывает входящие события, команду `/start` и callback-кнопки;
- `max_sender.py` отправляет приглашения и вопросы опросов.

Отправка и прохождение опроса учитывают сохранённый прогресс ученика. Повторная отправка не должна повторно запускать уже начатое прохождение.

### 3.8. Планировщик

`scheduler.py` отвечает за обработку очереди уведомлений и контроль сроков опросов.

Реализованы:

- проверка временных окон отправки с учётом часового пояса школы;
- пакетная обработка уведомлений;
- ограничение количества попыток;
- повторные попытки отправки;
- восстановление зависших отправок;
- heartbeat и lease для контроля выполняющейся задачи;
- защита от устаревших попыток отправки;
- закрытие просроченных прохождений;
- удаление неактуальных черновиков.

Основные параметры планировщика:

| Параметр | Значение |
|---|---:|
| Интервал проверки очереди | 60 секунд |
| Максимум попыток отправки | 3 |
| Тайм-аут зависшей отправки | 10 минут |
| Размер пакета уведомлений | 20 |
| Интервал heartbeat | 60 секунд |
| Задержка повторной попытки | 5 минут |

**Безопасный режим:** реальная отправка уведомлений отключена по умолчанию. Для её включения используется `SEND_NOTIFICATIONS=true`.

Не включайте отправку на рабочей базе без проверки конфигурации и отдельного подтверждения.

## 4. Подготовка окружения

Для разработки необходимы:

- Python 3.13;
- uv;
- PostgreSQL.

Перейдите в каталог backend:

```bash
cd backend
```

Создайте виртуальное окружение и установите зависимости:

```bash
uv sync --dev
```

Команда устанавливает зависимости проекта из `pyproject.toml` с учётом версий, зафиксированных в `uv.lock`.

## 5. Переменные окружения

В каталоге `backend` создайте файл `.env`.

Пример:

```env
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE
JWT_SECRET_KEY=your_long_random_secret
BOT_TOKEN=your_max_bot_token

# Необязательные параметры
FRONTEND_URL=http://127.0.0.1:8000
SEND_NOTIFICATIONS=false
DEMO_MODE=false
```

Назначение переменных:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `FRONTEND_URL` | Ссылка(и) на разрешённый(ые) ресурсы для API |
| `JWT_SECRET_KEY` | Секретный ключ для создания и проверки JWT |
| `BOT_TOKEN` | Токен MAX-бота |
| `SEND_NOTIFICATIONS` | Разрешение реальной отправки уведомлений планировщиком |
| `DEMO_MODE` | Режим работы демонстрационных операций |

Для автоматизированных тестов дополнительно используется `TEST_DATABASE_URL`, указывающий на отдельную тестовую базу данных.

Обязательные переменные должны быть заданы для соответствующих процессов. Например, MAX-бот требует `BOT_TOKEN`, а API и планировщик — корректного подключения к базе данных.

**Безопасность:**

- Не добавляйте `.env` в Git.
- Не публикуйте токены и секретные ключи.
- Не используйте рабочую базу для тестов.
- Не включайте `SEND_NOTIFICATIONS=true` без проверки целевой конфигурации.

## 6. Работа с базой данных и миграциями

Для управления схемой PostgreSQL используется Alembic.

Перед применением миграций проверьте подключение и целевую базу данных.

Посмотреть текущую ревизию:

```bash
uv run alembic current
```

Посмотреть историю миграций:

```bash
uv run alembic history
```

Посмотреть SQL, который будет выполнен при обновлении:

```bash
uv run alembic upgrade head --sql
```

Применить миграции:

```bash
uv run alembic upgrade head
```

**Важно:** миграции изменяют структуру базы данных. Перед применением на рабочей базе необходимо проверить целевое подключение, изучить миграции и подготовить резервную копию. Не запускайте миграции на production автоматически.

Новые изменения структуры БД оформляются отдельными миграциями Alembic. Не изменяйте уже применённые миграции вместо создания новых.

## 7. Запуск компонентов

Все команды ниже выполняются из каталога `backend`.

### 7.1. REST API

```bash
uv run uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

После запуска:

- API: `http://127.0.0.1:8000/`
- Swagger UI: `http://127.0.0.1:8000/docs`
- OpenAPI JSON: `http://127.0.0.1:8000/openapi.json`

Для остановки нажмите `Ctrl+C`.

Параметр `--reload` предназначен для локальной разработки.

### 7.2. MAX-бот

```bash
uv run python max_bot.py
```

Для работы необходимы `BOT_TOKEN` и доступ к той же базе данных, с которой работает API.

### 7.3. Планировщик

```bash
uv run python scheduler.py
```

По умолчанию планировщик работает в безопасном режиме и не отправляет реальные уведомления.

Для включения отправки необходимо явно установить:

```env
SEND_NOTIFICATIONS=true
```

Перед включением убедитесь, что используется нужная база данных и правильный токен MAX.

## 8. API-маршруты

Основные группы маршрутов:

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/` | Проверка доступности API |
| `POST` | `/api/auth` | Авторизация через MAX |
| `POST` | `/api/demo_auth` | Демонстрационная авторизация |
| `GET` | `/api/schools` | Доступные школы пользователя |
| `GET` | `/api/schools/{school_id}/classes` | Классы школы |
| `GET` | `/api/schools/{school_id}/classes/{class_id}/heatmap` | Дневная нагрузка класса |
| `GET` | `/api/schools/{school_id}/classes/{class_id}/summary` | Сводная нагрузка класса |
| `GET` | `/api/schools/{school_id}/classes/{class_id}/recommendations` | Рекомендации по нагрузке |
| `GET` | `/api/schools/{school_id}/classes/{class_id}/schedule` | Расписание класса |
| `PUT` | `/api/schools/{school_id}/classes/{class_id}/schedule/{lesson_id}` | Редактирование занятия |
| `POST` | `/api/schools/{school_id}/classes/{class_id}/schedule/{lesson_id}/editing` | Начало сессии редактирования |
| `PUT` | `/api/schools/{school_id}/classes/{class_id}/schedule/{lesson_id}/editing` | Продление сессии редактирования |
| `DELETE` | `/api/schools/{school_id}/classes/{class_id}/schedule/{lesson_id}/editing` | Завершение сессии редактирования |
| `GET` | `/api/schools/{school_id}/survey-classes` | Классы, доступные для просмотра статистики опросов |
| `GET` | `/api/schools/{school_id}/classes/{class_code}/surveys` | Список дат опросов класса |
| `GET` | `/api/schools/{school_id}/classes/{class_code}/surveys/{survey_date}` | Статистика опроса |

Для некоторых ресурсов предусмотрены маршруты, принимающие идентификатор школы и код класса. Полный перечень маршрутов, схемы запросов и ответов доступны в Swagger UI.

## 9. Автоматизированные тесты

Тесты расположены в каталоге `tests/`.

Основные направления проверки:

- авторизация и JWT;
- разграничение доступа;
- доступ к школам и классам;
- права на редактирование расписания;
- сессии редактирования;
- ограничения целостности PostgreSQL;
- работа MAX-бота и callback;
- отправка приглашений и вопросов;
- сохранение ответов и прогресса опросов;
- статистика опросов;
- управление доступом и перенос назначений учителей;
- планировщик уведомлений и повторные попытки.

### Настройка тестовой базы

Для тестов PostgreSQL необходимо создать отдельную базу и указать её в `TEST_DATABASE_URL`.

Пример для локального PostgreSQL:

```bash
export TEST_DATABASE_URL='postgresql+psycopg://USER:PASSWORD@localhost:5432/bluesphere_test'
```

Запустить весь набор тестов:

```bash
uv run python -m pytest -v
```

Запустить тесты конкретного модуля:

```bash
uv run python -m pytest -v tests/test_survey_service.py
```

Проверить ограничения PostgreSQL:

```bash
uv run python -m pytest -v tests/test_postgres_constraints.py
```

Тесты должны выполняться только на специально подготовленной тестовой базе. Не указывайте в `TEST_DATABASE_URL` адрес production-базы.

## 10. Вспомогательные скрипты

Служебные скрипты находятся в `scripts/` и запускаются как Python-модули из каталога `backend`.

Примеры:

```bash
uv run python -m scripts.seed
uv run python -m scripts.seed_schedule
uv run python -m scripts.check_schedule_conflicts
```

Основные скрипты:

| Скрипт | Назначение |

## 11. Docker

Для отдельных компонентов backend предусмотрены Dockerfile:

- `Dockerfile.api` — REST API;
- `Dockerfile.bot` — MAX-бот;
- `Dockerfile.scheduler` — планировщик.

В корне репозитория находится `docker-compose.yml`, который описывает запуск компонентов. Для локального Docker-окружения предусмотрен вспомогательный скрипт `scripts/docker_compose.py`.

При запуске через Docker необходимо корректно передать переменные окружения, в первую очередь `DATABASE_URL`. Для планировщика отправка уведомлений также должна оставаться отключённой, пока не проверена конфигурация.

## 12. Правила разработки

1. Изменения структуры БД оформляются новыми миграциями Alembic.
2. ORM-модели размещаются в `models.py`.
3. API-маршруты и проверки доступа находятся в `main.py`.
4. Логику работы с опросами следует размещать в соответствующих сервисных модулях.
5. Обработку событий MAX и отправку сообщений необходимо сохранять разделёнными между `max_bot.py` и `max_sender.py`.
6. Логику очереди и повторных попыток уведомлений следует поддерживать в `scheduler.py`.
7. Новая функциональность должна сопровождаться автоматизированными тестами.
8. Тесты должны использовать отдельную тестовую базу данных.
9. Необходимо сохранять транзакционную целостность, проверки прав доступа и защиту от повторной обработки операций.
10. Реальную отправку сообщений MAX нельзя включать без проверки окружения и явного разрешения.
