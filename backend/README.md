# Blue Sphere — Backend

Backend приложения **Blue Sphere** — REST API для школьного приложения, разработанный на Python с использованием FastAPI, SQLAlchemy и PostgreSQL.

Backend отвечает за авторизацию пользователей, работу со школами и классами, получение расписания, отображение школьной нагрузки, рекомендации и управление правами доступа.

## 1. Технологии

- Python 3.13
- FastAPI — REST API
- Uvicorn — ASGI-сервер
- SQLAlchemy — работа с базой данных
- PostgreSQL — СУБД
- Alembic — управление миграциями
- Pydantic — проверка и сериализация данных
- psycopg — драйвер PostgreSQL
- Pytest — автоматизированное тестирование
- uv — управление зависимостями и виртуальным окружением

## 3. Подготовка окружения

Для работы необходимо установить:

- Python 3.13;
- uv;
- PostgreSQL.

Перейдите в каталог backend:

```bash
cd backend
```

Создайте виртуальное окружение и установите зависимости проекта:

```bash
uv sync --dev
```

Команда установит зависимости из `pyproject.toml` и версии пакетов, зафиксированные в `uv.lock`, включая инструменты для тестирования.

### Настройка переменных окружения

В папке `backend` необходимо создать файл `.env`. Он содержит настройки подключения к базе данных и авторизации.

Пример содержимого:

```env
DATABASE_URL=ваша_строка_подключения_к_PostgreSQL
JWT_SECRET_KEY=случайная_длинная_секретная_строка
BOT_TOKEN=токен_бота_MAX
```

- `DATABASE_URL` — строка подключения к PostgreSQL.
- `JWT_SECRET_KEY` — секретный ключ для создания и проверки JWT-токенов.
- `BOT_TOKEN` — токен MAX-бота, необходимый для проверки данных авторизации MAX.

Значения необходимо получить из соответствующих настроек проекта. Не используйте приведённые в примере обозначения вместо настоящих значений.

**Важно:** файл `.env` содержит секретные данные. Не добавляйте его в Git, не отправляйте в публичные репозитории и не передавайте третьим лицам. Для тестирования используйте отдельную базу данных, а не рабочую.

## 5. Подготовка базы данных

Для управления структурой базы данных используется Alembic.

Перед применением миграций убедитесь, что:

1. PostgreSQL запущен.
2. В `.env` указан правильный `DATABASE_URL`.
3. Создана резервная копия базы данных.
4. Вы точно знаете, к какой базе подключается приложение.

Проверить текущую ревизию Alembic:

```bash
uv run alembic current
```

Посмотреть список миграций:

```bash
uv run alembic history
```

Применить все доступные миграции:

```bash
uv run alembic upgrade head
```

Миграции обновляют структуру существующей базы данных. Они не предназначены для замены рабочей базы тестовой.

**Не запускайте `alembic upgrade head` на рабочей базе без предварительной проверки миграций и резервного копирования.**

## 6. Запуск API

Из каталога `backend` выполните:

```bash
uv run uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

После запуска API будет доступно по адресам:

- Главная страница: http://127.0.0.1:8000/
- Swagger UI: http://127.0.0.1:8000/docs
- OpenAPI JSON: http://127.0.0.1:8000/openapi.json

Для остановки сервера нажмите `Ctrl+C`.

Параметр `--reload` предназначен для разработки: сервер автоматически перезапускается при изменении файлов.

## 7. Авторизация и доступ

Авторизация пользователей приложения связана с MAX Mini App.

API принимает данные `initData`, проверяет их и выдаёт JWT-токен. Далее токен используется для обращения к защищённым API-маршрутам.

Доступ к школам и данным зависит от роли пользователя:

- **Ученик** — доступ к собственной школе и текущему классу.
- **Учитель** — доступ к школам, в которых он зарегистрирован, и классам, в которых у него есть назначения.
- **Администратор** — доступ к школе, в которой он зарегистрирован, и её классам.

Если у пользователя несколько ролей, доступ определяется объединением разрешений этих ролей.

Основные маршруты API доступны через Swagger UI по адресу `/docs`.

## 8. Автоматизированные тесты

Для проверки backend используется Pytest.

Тесты расположены в каталоге `tests/` и проверяют, в частности:

- авторизацию и доступ пользователей;
- разграничение прав по ролям;
- доступ к школам и классам;
- права на редактирование расписания;
- работу сессий редактирования;
- ограничения целостности PostgreSQL.

### Настройка тестовой базы

Тесты PostgreSQL используют отдельную базу данных.

Перед запуском необходимо создать тестовую базу и настроить переменную `TEST_DATABASE_URL`.

Пример для локального PostgreSQL:

```bash
export TEST_DATABASE_URL='postgresql+psycopg://ПОЛЬЗОВАТЕЛЬ@/ИМЯ_ТЕСТОВОЙ_БАЗЫ?host=/var/run/postgresql'
```

Тестовая конфигурация проекта проверяет имя и параметры подключения, чтобы не допустить случайного запуска интеграционных тестов на рабочей базе.

**Не указывайте в `TEST_DATABASE_URL` адрес рабочей базы данных.**

Запуск всех тестов:

```bash
uv run python -m pytest -v
```

Запуск только тестов PostgreSQL:

```bash
uv run python -m pytest -v tests/test_postgres_constraints.py
```

Тесты используют транзакции с откатом после выполнения, поэтому созданные в ходе тестирования данные не должны сохраняться в тестовой базе.

## 9. Вспомогательные скрипты

В каталоге `scripts/` находятся инструменты для обслуживания базы данных и демонстрационных данных.

Скрипты запускаются из каталога `backend` как Python-модули.

Например:

```bash
uv run python -m scripts.seed
```

Назначение скриптов:

| Скрипт | Назначение |
|---|---|
| `seed.py` | Создание демонстрационной школы, учебного года и классов |
| `seed_schedule.py` | Создание демонстрационных назначений и расписания |
| `add_admin.py` | Назначение пользователю роли администратора |
| `create_teacher.py` | Создание пользователя и роли учителя |
| `create_test_student.py` | Создание тестового ученика и первоначального зачисления |
| `check_schedule_conflicts.py` | Поиск конфликтов в расписании |
| `fix_demo_schedule.py` | Исправление демонстрационного расписания |
| `update_demo_schedule.py` | Обновление демонстрационного расписания |

Для запуска другого скрипта используется аналогичная команда. Например:

```bash
uv run python -m scripts.check_schedule_conflicts
```

Скрипты, создающие или изменяющие данные, следует запускать только после проверки целевой базы данных.

**Не запускайте скрипты создания пользователей, заполнения или изменения расписания на рабочей базе без понимания последствий.** Перед такими операциями рекомендуется создать резервную копию.

## 10. Запуск MAX-бота

Для запуска MAX-бота необходимо настроить `BOT_TOKEN` в файле `.env`.

Из каталога `backend` выполните:

```bash
uv run python max_bot.py
```

Для корректной работы бот должен иметь доступ к той же базе данных, с которой работает API, и к действующему токену MAX.

## 11. Правила разработки

- Изменения структуры базы данных оформляются миграциями Alembic.
- Модели таблиц описываются в `models.py`.
- API-маршруты и основная серверная логика находятся в `main.py`.
- Подключение к базе данных настраивается через `database.py`.
- Секретные данные хранятся в `.env`, а не в исходном коде.
- После изменения логики необходимо запускать автоматизированные тесты.
- Для проверки изменений базы данных следует использовать отдельную тестовую базу.
- Демонстрационные данные не должны использоваться для замены или перезаписи рабочих данных.
- Файл `uv.lock` необходимо обновлять при изменении зависимостей и включать в Git вместе с `pyproject.toml`.
