# Blue Sphere — Backend

Backend приложения **Blue Sphere** — серверная часть системы планирования учебной нагрузки.

Реализован на Python с использованием FastAPI, SQLAlchemy и PostgreSQL.

Backend отвечает за:
- REST API;
- авторизацию пользователей через MAX Mini App;
- управление школами, учебными годами и классами;
- расписание и редактирование занятий;
- разграничение доступа по ролям;
- опросы учеников и агрегированную статистику;
- MAX Bot;
- планирование уведомлений;
- очередь AI-задач и сохранение прогнозов нагрузки.

Инструкция по запуску всего проекта через Docker Compose находится в корневом [README.md](../README.md).

## 3. Основные модули

### 3.1. `main.py`

Главный модуль FastAPI.

Содержит:
- создание приложения;
- REST-маршруты;
- авторизацию и проверку JWT;
- проверку ролей и принадлежности к школе;
- получение классов и расписания;
- тепловую карту нагрузки;
- сводку нагрузки;
- рекомендации;
- редактирование расписания;
- сессии редактирования;
- статистику опросов.

Проверки доступа выполняются на стороне backend. Frontend не является доверенной стороной.

### 3.2. `database.py`

Создаёт подключение к PostgreSQL на основе `DATABASE_URL`.

Содержит:
- SQLAlchemy Engine;
- фабрику сессий `SessionLocal`;
- базовый класс ORM-моделей;
- инфраструктуру доступа к БД.

### 3.3. `models.py`

Содержит ORM-модели и связи между таблицами.

Основные группы сущностей:

- школы и учебные годы;
- классы;
- пользователи и роли;
- ученики и зачисления;
- учителя и предметные назначения;
- расписание;
- сессии редактирования;
- шаблоны и экземпляры опросов;
- вопросы и варианты ответов;
- прогресс прохождения опросов;
- AI-задачи, результаты анализа, прогнозы и рекомендации.

Изменение структуры БД выполняется через новую миграцию Alembic, а не ручным редактированием существующей схемы.

### 3.4. `survey_instance_service.py`

Отвечает за подготовку экземпляров опросов:
- поиск классов с расписанием на дату;
- подготовку вариантов ответов;
- формирование экземпляров опросов;
- учёт часового пояса школы;
- предотвращение повторного создания экземпляров.

### 3.5. `survey_service.py`

Бизнес-логика прохождения опросов:
- получение доступных вопросов;
- проверка вариантов ответов;
- сохранение одиночных и множественных ответов;
- работа с черновиками;
- управление прогрессом;
- завершение и закрытие опросов;
- формирование агрегированной статистики.

### 3.6. `max_bot.py`

Обрабатывает входящие события MAX:
- команду `/start`;
- определение пользователя;
- восстановление незавершённого опроса;
- callback-кнопки;
- переходы между вопросами;
- продолжение прохождения опроса.

### 3.7. `max_sender.py`

Отправляет сообщения через MAX:
- приглашения к прохождению опросов;
- вопросы;
- варианты ответов;
- сообщения, связанные с прогрессом опроса.

Разделение входящей логики и отправки сообщений упрощает тестирование и поддержку.

### 3.8. `scheduler.py`

Фоновый планировщик.

Отвечает за:
- проверку сроков опросов;
- формирование уведомлений;
- контроль временных окон;
- повторные попытки;
- исключение демонстрационных пользователей из реальных уведомлений;
- постановку AI-задач в очередь.

Планировщик запускается отдельным процессом.

### 3.9. `workload.py`

Содержит функции расчёта учебной нагрузки.

Основные функции:

- `get_daily_lesson_counts()` — подсчитывает количество уроков класса по дням, не удваивая занятия разных подгрупп;
- `get_load_level()` — переводит количество уроков в уровень нагрузки.

Уровни:

| Уровень | Значение |
|---|---|
| `0` | Перегрузка |
| `1` | Высокая нагрузка |
| `2` | Средняя нагрузка |
| `3` | Низкая нагрузка |
| `4` | Очень лёгкий день |
| `None` | Уроков нет |

Текущая базовая шкала:
- 1–3 урока — уровень 4;
- 4 урока — уровень 3;
- 5 уроков — уровень 2;
- 6 уроков — уровень 1;
- 7 и более уроков — уровень 0.

## 4. AI-подсистема

AI-логика разделена на независимые модули.

| Файл | Ответственность |
|---|---|
| `ai_config.py` | Основной и резервный провайдеры, таймауты и лимиты |
| `ai_provider.py` | HTTP-запросы к совместимому AI API и обработка ошибок |
| `ai_prompts.py` | Инструкции и версии промптов |
| `ai_schemas.py` | Проверка структуры AI-ответов |
| `ai_context.py` | Сбор расписания и агрегатов опросов |
| `ai_service.py` | Оркестрация вызова AI и обработки результата |
| `ai_aggregation.py` | Агрегация результатов |
| `ai_queue.py` | Постановка, получение и завершение задач |
| `ai_worker.py` | Фоновое выполнение задач |

### 4.1. Конфигурация

Основной провайдер задаётся переменными:

```env
AI_BASE_URL=
AI_TOKEN=
AI_MODEL=
```

Резервный:

```env
AI_FALLBACK_BASE_URL=
AI_FALLBACK_TOKEN=
AI_FALLBACK_MODEL=
```

Дополнительные параметры:

```env
AI_TIMEOUT_SECONDS=60
AI_MAX_OUTPUT_TOKENS=4000
```

Точный формат `AI_BASE_URL` зависит от провайдера и используемого API.

Наличие конфигурации не гарантирует доступность модели. Работоспособность необходимо проверять по логам worker и ответам конкретного провайдера.

### 4.2. Очередь и Worker

AI-задачи хранятся в базе данных.

Worker:
1. получает доступную задачу;
2. захватывает её на обработку;
3. формирует контекст;
4. вызывает AI-сервис;
5. валидирует результат;
6. сохраняет прогнозы и рекомендации;
7. отмечает задачу завершённой либо планирует повторную попытку.

Для защиты от параллельной обработки используются механизмы захвата задачи и контроля актуальности lease.

### 4.3. Ограничения входных данных

В AI-контекст передаются расписание и агрегированные результаты опросов.

AI не должен получать:
- индивидуальные ответы учеников;
- идентификаторы учеников;
- персональные сведения об участниках опроса.

Прогнозы относятся к конкретному классу и дате. Сохранённые прогнозы используются API для отображения тепловой карты.

## 5. Авторизация и роли

Авторизация Mini App выполняется через `initData` MAX.

Основной маршрут:

```http
POST /api/auth
```

Backend проверяет данные MAX и возвращает JWT.

Защищённые маршруты используют:

```http
Authorization: Bearer <access_token>
```

В проекте предусмотрены роли:

- `student`;
- `teacher`;
- `admin`.

Основные правила доступа:

| Роль | Доступ |
|---|---|
| Ученик | Собственная школа и класс |
| Учитель | Классы с соответствующими предметными назначениями или выданным доступом |
| Администратор | Классы своей школы |

Доступ учителя к классу и предметное назначение учителя — разные сущности.

Ученик не получает доступ к AI-рекомендациям.

Статистика опросов возвращается в агрегированном виде, без индивидуальных ответов и идентификаторов учеников.

## 7. Переменные окружения

Пример конфигурации находится в `.env.example`.

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение к PostgreSQL |
| `JWT_SECRET_KEY` | Секрет подписи JWT |
| `BOT_TOKEN` | Токен MAX Bot |
| `FRONTEND_URL` | Разрешённые frontend-origin |
| `DEMO_MODE` | Режим демонстрационных пользователей |
| `SEND_NOTIFICATIONS` | Разрешение отправки уведомлений |
| `AI_BASE_URL` | Основной AI endpoint |
| `AI_TOKEN` | Основной AI token |
| `AI_MODEL` | Основная модель |
| `AI_FALLBACK_BASE_URL` | Резервный endpoint |
| `AI_FALLBACK_TOKEN` | Резервный token |
| `AI_FALLBACK_MODEL` | Резервная модель |
| `AI_TIMEOUT_SECONDS` | Таймаут AI |
| `AI_MAX_OUTPUT_TOKENS` | Максимальный размер AI-ответа |

### DEMO_MODE

```env
DEMO_MODE=true
```

Создаваемые скриптами пользователи получают признак демонстрационного пользователя.

```env
DEMO_MODE=false
```

Создаваемые пользователи относятся к обычному режиму.

Нельзя запускать скрипт в одном режиме для пользователя, который уже существует в другом режиме.

### SEND_NOTIFICATIONS

```env
SEND_NOTIFICATIONS=false
```

Отключает реальную отправку уведомлений планировщиком.

Для включения отправки требуется:

```env
SEND_NOTIFICATIONS=true
```

Перед этим необходимо проверить токен MAX, базу данных и целевую аудиторию.

## 8. Локальная установка и запуск без Docker

Команды выполняются из каталога `backend`.

### 8.1. Установка uv

Если `uv` ещё не установлен, установи его согласно официальной инструкции проекта uv.

Проверка:

```bash
uv --version
```

### 8.2. Подготовка окружения

```bash
cd backend
cp .env.example .env
```

Заполни `.env`, особенно `DATABASE_URL`, `JWT_SECRET_KEY` и `BOT_TOKEN`.

```bash
uv sync
```

```bash
uv sync --all-groups
```

```bash
uv run alembic upgrade head
```

Проверка текущей версии:

```bash
uv run alembic current
```

```bash
uv run alembic history
```

```bash
uv run uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

```bash
uv run python ai_worker.py
```

## 9. Миграции Alembic

Файлы миграций находятся в:

```text
migrations/versions/
```

Создание новой миграции:

```bash
uv run alembic revision -m "описание изменения"
```

Автогенерация на основе ORM-моделей:

```bash
uv run alembic revision --autogenerate -m "описание изменения"
```

Автогенерируемую миграцию обязательно проверь вручную.

Применение:

```bash
uv run alembic upgrade head
```

Откат на одну миграцию:

```bash
uv run alembic downgrade -1
```

Просмотр истории:

```bash
uv run alembic history
```

Текущая версия:

```bash
uv run alembic current
```

Не изменяй миграции, которые уже были применены на рабочей базе. Для новых изменений создавай следующую миграцию.

Перед production-миграцией требуется резервная копия и проверка SQL-изменений.

## 10. Служебные скрипты

Все скрипты находятся в `scripts/`.

Запуск из каталога `backend`:

```bash
uv run python scripts/ИМЯ_СКРИПТА.py
```

Скрипты, запрашивающие данные через `input()`, запускаются в интерактивном терминале.

### 10.1. `scripts/user_mode.py`

Общие функции режима работы:
- `is_demo_mode()` — читает `DEMO_MODE`;
- `get_or_create_user()` — получает или создаёт пользователя с проверкой режима;
- `get_user_by_sferum_id()` — ищет пользователя и проверяет его режим;
- `validate_database_mode()` — проверяет режим и защищённую базу.

База `bluesphere_restore_test` защищена от запуска скриптов изменения данных.

### 10.2. `scripts/seed.py`

```bash
uv run python scripts/seed.py
```

Создаёт или находит:
- школу № 1;
- учебный год `2026-2027`;
- 44 класса с 1-го по 11-й;
- параллели А, Б, В и Г.

Скрипт предназначен для начального демонстрационного наполнения.

### 10.3. `scripts/seed_schedule.py`

```bash
uv run python scripts/seed_schedule.py \
  --start-date 2026-09-01 \
  --end-date 2026-09-30
```

Аргументы:
- `--start-date` — начало периода;
- `--end-date` — конец периода.

Обе даты обязательны, формат `YYYY-MM-DD`.

Создаёт демонстрационные предметы, учителей, назначения и расписание по будним дням.

### 10.4. `scripts/seed_survey_questions.py`

```bash
uv run python scripts/seed_survey_questions.py
```

Создаёт или обновляет три шаблона опросов:
1. оценка состояния после учебного дня;
2. предметы, вызывавшие тревогу;
3. предметы, которые давались легко.

Скрипт идемпотентный: повторный запуск обновляет шаблоны и варианты, не создавая дубликаты этих записей.

### 10.5. `scripts/create_survey_instances.py`

Предварительный просмотр:

```bash
uv run python scripts/create_survey_instances.py --date 2026-09-09
```

Фактическое создание:

```bash
uv run python scripts/create_survey_instances.py \
  --date 2026-09-09 \
  --create
```

Аргументы:
- `--date` — дата опроса;
- `--create` — разрешает запись экземпляров в БД.

Без `--create` скрипт работает в режиме предварительного просмотра.

## 12. Работа с конфиденциальными данными

1. Статистика опросов возвращается агрегированно.
2. Индивидуальные ответы учеников не должны передаваться в статистические API.
3. AI-контекст не должен содержать персональные данные учеников.
4. Ученик не имеет доступа к AI-рекомендациям.
5. Проверка прав доступа выполняется backend, а не только frontend.
6. Демонстрационные пользователи отделяются через `User.is_demo` и `DEMO_MODE`.
7. Реальная отправка уведомлений должна быть явно разрешена настройкой `SEND_NOTIFICATIONS`.

## 13. Правила разработки

1. Новые изменения структуры БД оформляются отдельными миграциями Alembic.
2. Уже применённые миграции не редактируются.
3. API-маршруты и проверки доступа размещаются в `main.py`.
4. ORM-модели размещаются в `models.py`.
5. Бизнес-логику опросов следует размещать в `survey_service.py` и `survey_instance_service.py`.
6. Обработку входящих событий MAX и отправку сообщений необходимо разделять.
7. Планирование задач и отправка уведомлений относятся к `scheduler.py`.
8. AI-подсистема сохраняет разделение конфигурации, контекста, промптов, провайдера, схем, сервиса, очереди и worker.
9. Новая функциональность должна сопровождаться тестами.
10. Тесты должны использовать отдельную базу.
11. Проверки доступа должны выполняться на сервере.
12. Персональные ответы учеников не передаются AI.
13. Не включай реальные уведомления без проверки окружения и явного разрешения.
